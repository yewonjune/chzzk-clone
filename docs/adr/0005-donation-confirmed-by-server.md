# 도네이션은 서버가 PG에 승인을 확인한 뒤에만 확정하고, 확정은 주문 행 잠금으로 한 번만 한다

결제창이 돌려준 성공 화면은 브라우저가 만든 값이라 금액·주문번호를 고칠 수 있고, 같은 승인 통지(결과 화면 새로고침, PG 웹훅 재전송)는 여러 번 올 수 있다. 그래서 결제창을 열기 전에 서버가 PENDING 주문을 만들어 금액과 받는 사람(그 방송의 소유자)을 고정하고, 돌아온 값은 이 주문과 대조한 뒤 PG 승인 API의 응답(상태 DONE, 주문번호, 금액)을 한 번 더 대조해서 맞을 때만 PAID로 바꾼다. 웹훅은 보낸 쪽을 믿을 수 없으므로 본문은 쓰지 않고 `paymentKey`로 PG에 다시 조회한 결과만 반영한다.

중복 적립은 "주문 행을 `SELECT … FOR UPDATE`로 잠그고 PENDING → PAID 전이를 한 번만 허용"하는 방식으로 막는다. 합계는 PAID 행의 SUM이라 따로 잔액 컬럼을 두지 않으며, 전이가 한 번이면 적립도 한 번이다. `payment_key` UNIQUE가 한 결제를 두 주문에 쓰는 경우를 DB 수준에서 막는다. 처리 기록 테이블(웹훅 이벤트 ID 저장)도 검토했지만, 토스페이먼츠 결제 웹훅에는 안정적인 이벤트 ID가 없고 주문 상태 자체가 멱등성의 기준이 되므로 두지 않았다.

PG와 통신이 끊겨 승인 결과를 모를 때는 FAILED로 바꾸지 않는다. 실제로는 승인됐을 수 있으므로 PENDING으로 두고, 웹훅이나 재요청(PG가 ALREADY_PROCESSED_PAYMENT를 돌려주면 결제를 조회해 확인)으로 확정한다. 실제 금전 결제를 막기 위해 토스페이먼츠는 `test_` 키만 받고, 키가 없으면 같은 2단계 흐름을 흉내 내는 내장 가짜 PG로 동작한다.
